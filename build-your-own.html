Build your own

You do not need a team to run a product company. You need one person who can make the release call, and a small set of agents and gates that do the rest. Here is the pattern this project actually runs on, what to copy first, what it costs, and what it got wrong along the way.

One person, one product, many agents

Xpired is built and run by one founder. The team is not a headcount, it is a set of AI agents with narrow jobs: one writes code, one watches production every morning, one triages shopper feedback, one drafts release notes. None of them is a person, and none of them has a title. The founder is the only human in the loop, and every agent's output still routes through that one person before it reaches a shopper.

Agents write. Gates verify. A human presses release.

This is the one rule everything else in this guide is built to protect. An agent can open a pull request, draft a fix, or flag an anomaly. An automated gate can block a merge or fail a check. Neither one can be the last signature on anything that reaches a real user.

Agents write. Code changes, release notes, and Slack digests all start as an agent's draft. Nothing an agent produces is trusted just because an agent produced it.
Gates verify. Required checks run on every pull request and read their pass/fail from a real test collection, not a hand-typed count, so a deleted test cannot quietly shrink the gate. See the automation inventory for what those checks actually are.
A human presses release. The release workflow only runs when the founder dispatches it. No scheduler, watcher, or agent in this project is allowed to submit a build or promote a deploy on its own; the one place this shows up concretely today is the ledger's entry on the 4.3.6 App Store submission, still waiting on the founder's decision even though the review itself is out of anyone's hands.

The minimum stack to copy

Five pieces, all of them already running in this project. Every claim below is cited to the automation inventory, the single page that has to stay honest about what actually runs.

Required checks that fail closed. Every pull request runs the required checks (release-contracts and asc-gate-tests, plus shopper-tests on iOS paths) before anything can merge. The test count is derived from collection at run time, not typed by hand, so a deleted suite fails the gate instead of shrinking it quietly.
Canary, then promote, never rebuild. The release workflow (fly-deploy.yml) builds one image, checks a canary with a signed probe, and promotes that exact same digest to production. It never rebuilds between the canary check and the production release, and it rolls back on failure.
A release runbook that never has real authority by itself. A daily dry-run exercises the whole release path every morning without ever being allowed to submit anything; the real submit step still waits on a separate readiness check reading true, and on the founder's own decision.
A nightly steward that reports, never applies. A daily steward watches code quality, storage, deployment, and activity, and posts what it finds to the team's Slack channel every morning. It can draft a fix card. It can never apply one; a person still decides.
A Slack channel as the one operator inbox. The morning feedback digest and the flywheel steward both land in the same Slack channel, so the founder triages from one place instead of five separate logs. A separate Slack bot answers grounded questions from immutable snapshots of the repository, on request, and never edits anything itself.

What to copy first, in order

Build the floor before the roof. Each step below only works because the one before it already holds.

  1. Required checks that fail closed

    Before anything else, make it impossible to merge a change that breaks the build or silently drops a test. This is the one piece every other automation in this stack quietly depends on: a steward, a canary, or a digest is only trustworthy if the code underneath it already has to pass a real gate.

  2. Canary and promote

    Once merges are safe, make releases safe the same way: build once, check the canary, promote the exact digest that passed. This is the step that turns "it built" into "it is safe to show a user."

  3. A release runbook with no real authority

    Rehearse the release path daily without letting it submit anything. This surfaces a broken release path on a quiet Tuesday instead of the morning you actually need to ship.

  4. A nightly steward

    Once the floor is solid, add a watcher that reports drift across quality, storage, deployment, and activity. It is the cheapest way to find a slow problem before a person would have noticed it.

  5. One Slack channel as the inbox

    Last, not first: route everything the checks, the canary, and the steward produce into one channel. Routing is only worth building once there is real signal to route.

What it costs

Small. The specifics, the parts of this that cost real money and the parts that ran free, are tracked honestly in the program ledger rather than summarized here, because a summary is exactly the kind of number this guide promised not to invent.

Three lessons this project learned the hard way

Pulled directly from the program ledger, with the entry each one comes from, so you can go read the original rather than trust a summary.

REPORTED

A test command that silently returns nothing is worse than one that errors.

The documented command for the team's internal safety-test suite used to abort immediately with an internal error and run nothing at all, and it did that silently instead of failing loudly. It now runs cleanly and reports 301 passing tests from that single command, which is what every future check in this project relies on.

Source: the program ledger, entry L37, behind-the-scenes reliability lane.

REPORTED

A claim baked into the code needs the same proof as a claim in a document.

Small price-comparison badges in the shopper app were marked in the code as already reviewed for shoppers using larger text sizes, when they had not been, on a screen shoppers actually reach. The badges were clipping. The fix was only trusted once the team reverted it, watched the automated check fail exactly as expected, and then restored it to green.

Source: the program ledger, entry L20, shopper experience polish lane.

BLOCKED

The automation's job ends at the decision, not past it.

The version currently waiting on Apple's review should not go live the moment it is approved. Apple's review itself is out of anyone's hands, and the team lead wants everything release-ready today, but the release button stays the lead's own call. This row of the ledger only turns green once that decision is recorded, and nothing automated is allowed to make it first.

Source: the program ledger, entry L38, App Store submission lane.
