The automation inventory

Every automation has a job, a boundary, and a status. The boundary matters just as much as the job.

VERIFIEDINFERREDFLAG-GATED

How to read this inventory

Automation names and statuses are read from cited records. The classroom explanation of each boundary is a synthesis. A live row means the capability is active as described in its evidence, not that it can make every decision by itself. FLAG-GATED means the code is present but its current runtime state needs a flag readback.

Backend schedulers

These are in-process capabilities. Flag names identify the capability without exposing values.

One deliberately narrow predicate controls the three ML schedulers — plus, for two of the three, a scanner-runtime condition.

scheduler_flag_enabled() enables them only when a value spells true in any case; nothing else counts. Two of the three, continuous labeling and retraining, are additionally gated on the scanner runtime being enabled, so their flag alone is not enough to start them. The other two schedulers spell the same rule themselves. Every flag defaults off, and nothing in the repository turns one on.

DARK means built but not running in this release. FLAG-GATED means the code ships in the deployment and its current state requires runtime readback; the three ML schedulers share one predicate, while the other two spell the same rule themselves. With every flag defaulting off, reminder scheduling's live state is a runtime readback at /health/reminder-scheduler; feedback digest requires its own runtime readback, not an assumption from source. Not everything the backend starts is flag-gated: the application lifespan starts eight background tasks, and the two rows added above are the ones this table used to omit. The eighth is a one-shot warm-up of a hardcoded city list, which is not a scheduler.
