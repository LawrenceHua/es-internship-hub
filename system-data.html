Job in the loop

Keep each record useful and traceable.

A shopper needs the app to remember an item and its result. The backend saves that record, while a correction takes its own review path. ML can use only the approved subset, not every record in the database.

How it works

Save, check, separate.

01 / Write

Save the product record

The backend saves user, inventory and correction records through shared rules instead of letting every screen make up its own storage.

02 / Validate

Check what the record means

Rules for shape, ownership, consent and source determine what the record means and which jobs may use it.

03 / Separate

Make safe views for each job

The app, reporting and ML each use a purpose-specific view instead of treating the whole database as one pool.

Automation and tests

Safety before convenience.

  • Database startup is centralized.The FastAPI lifespan calls a manager; source still needs a live health reading before availability is claimed.
  • Digest and data-collection loops are feature-controlled.Source includes scheduler paths, but an environment flag, running process and semantic receipt are separate evidence.
  • Representative source checks address storage, corrections and data quality.tests/backend_tests/test_complete_storage_system.py, tests/test_correction_event.py and tests/test_data_quality_gates.py exist; that is not proof that a current run passed.

Critical boundary

Stored does not mean usable for everything.

Purpose and permission travel with the record. Product state, analytics, feedback and training data need different rules even when they share infrastructure.

Never inferA connection string, model class or database test does not establish live data, durability, consent or a current backup.
RequireSchema checks, scoped authorization, consent state, current runtime health and a recoverable maintenance plan before consequential changes.
